### 2.2 カスタムユーザーモデル ★ 第1部の最初に必ず置く

**理由**: Django は最初のマイグレーションで User モデルが固定される。あとから差し替えるには DB を作り直すしかない。コードは10行ほどで学習負担はほぼ無いが、入れ忘れると第3部で詰む。

`AbstractUser` を継承し、`settings.AUTH_USER_MODEL` を設定する。**「なぜ最初でないと駄目か」を仕組み解剖で必ず扱う。**
根拠: https://docs.djangoproject.com/en/stable/topics/auth/customizing/#using-a-custom-user-model

### 2.3 認証は JWT（django-ninja-jwt）

**第1部では認証を一切入れない。** 全エンドポイント公開で始める。最初から認証があると `curl` すら面倒になり、学習の入口で止まる。第2部で足す。

**セッション認証との違いを、第2部の該当ステップで必ず表にして示す**（サーバが状態を持つか / Cookie か ヘッダか / 即時ログアウトの可否 / CSRF 対策の要否）。
Django の管理画面はセッション認証のまま同居するので、**同じプロジェクト内で両方が動いているのを実際に見せる**。

### 2.4 管理画面は「道具」として使う。学習対象にしない ★

`admin.py` に `admin.site.register(Post)` 相当を書くだけ。**カスタマイズは一切扱わない。**

用途は「モデルが正しく作れたか」「画像が保存されたか」を目で確認すること。
初出時に **「これは学習対象ではなく、データを見るための窓」と明記する**。

### 2.5 拡張モジュール（任意・本編のあとで呼ぶ）

`docs/ext/` に置く。`MX: <name>` で1つずつ生成する。

| name | 内容 | 前提 | 新しく必要なもの |
| --- | --- | --- | --- |
| `celery` | 非同期処理（画像リサイズ・一括メール） | 第3部まで | Redis コンテナ |
| `websocket` | リアルタイム通知 | 第3部まで | Django Channels / Redis |
| `search` | 全文検索 | 第2部まで | Elasticsearch コンテナ |
| `cache` | キャッシュ機構 | 第2部まで | Redis コンテナ |
| `signals` | シグナル（と使いすぎの危うさ） | 第2部まで | なし |
| `drf` | DRF なら同じ API をどう書くか（比較のみ） | 第2部まで | djangorestframework |

**`MX` を呼ばれたら、まず前提を満たしているか確認する。** 満たしていなければ、何が足りないかを伝えて止まる。

`docs/ext/_index.md` に上の表を置き、各モジュールの**ステップ数の見込み**も書く。本編完了時に読者がここを見て選ぶ。

**モジュールを追加したくなったときは、この表に行を足せばよい**（例: OAuth、多言語対応は今回入れていないが、あとから足せる）。

### 2.6 素材ファイルの作り方

roadmap.sh/django のページは JavaScript で描画されるため URL からは読めない。
同じ内容が GitHub に Markdown で公開されているので、それを結合して使う。

```bash
git clone --depth 1 https://github.com/kamranahmedse/developer-roadmap.git /tmp/dr
find /tmp/dr -type d -path '*django/content' | head   # パス確認
for f in /tmp/dr/roadmaps/django/content/*.md; do
  echo -e "\n\n## $(basename "$f" .md)\n"; cat "$f"
done > docs/_roadmap-django-source.md
rm -rf /tmp/dr
```

**使い方のルール**

- **記事本文を教材化しない。** 1トピック数行しかなく、素材としては薄い
- トピック名は **「扱う範囲」の定義**として使う（M0 の対応表に使う）
- 解説の素材は、各トピックが張っている**公式ドキュメントのリンク先**を使う
- **SSR 系のトピック（テンプレート / フォーム / クラスベースビュー / 管理画面カスタマイズ / 静的ファイル）は、意図的な範囲外**として対応表に理由付きで載せる

ファイルが無ければ、推測で目次を作らず上のコマンドを案内して止まる。

## 4. 全モード共通の絶対ルール

### 4.1 やさしい言葉で書く ★ この教材の最優先ルール

**(a) 専門用語には必ず言い換えを添える**

正式名称は必ず書く（エラーや公式ドキュメントに出るため）。そのうえで、直後に必ずこれを置く。

> 🧒 **かみくだくと**: マイグレーションは「設計図の変更を、実物のテーブルに反映する作業」。
> 手で SQL を書く代わりに、Django が変更点を見つけて自動でやってくれる。

**(b) 文章の書き方**

- 1文を短く。**1文に読点は2つまで**
- 「〜であり、〜のため、〜という設計」のような積み重ねをしない。文を分ける
- カタカナ語を出したら、直後に日本語で言い換える
- 主語を省かない。「誰が」「何を」するのかを毎回書く

**(c) 共通のたとえ: 役所の窓口**

比喩を毎回変えない。1つを育てて使い回す。

| たとえ | 実際のもの | 初出 |
| --- | --- | --- |
| 窓口に来た人 | リクエスト | 第1部 |
| 受付の案内表 | URL ルーティング | 第1部 |
| 申請書の書式チェック | バリデーション（Ninja のスキーマ） | 第1部 |
| 担当職員 | ビュー関数 | 第1部 |
| 台帳 | データベースのテーブル | 第1部 |
| 台帳を書き換える手続き | マイグレーション | 第1部 |
| 台帳を代わりに引いてくれる職員 | ORM | 第1部 |
| 窓口の順路に置かれた共通の検査 | ミドルウェア | 第2部 |
| 身分証 | JWT トークン | 第2部 |

**(d) 図を入れる**

「積み重なり」「入れ子」「順番」「分かれ道」を説明するときは必ず図を入れる。飾りの図は入れない。

- 形式は**罫線の図**（コードブロックで囲む）を既定とする
- 日本語は半角の2倍幅。**表示幅を計算してから書く**。目視で揃えない
- 図の直後に「どこを見てほしいか」を1〜2行書く
- 分岐する流れは Mermaid の `flowchart` でもよい

### 4.3 🔬 仕組み解剖（4点セット）

Django / Ninja の記法・API・挙動が初出のとき、次の4点を必ず埋める。

1. **正式名称** — 公式ドキュメントでの呼び名
2. **実行時に何が起きるか** — Django / Ninja / Pydantic / MySQL のどれが、いつ、何をするか
3. **既知スタック（TypeScript / React）での対応物** — **無い場合は「対応物なし。理由は〜」と書く。これで4点セットを満たしたとみなす**
4. **なぜこの設計なのか** — 他の書き方との比較

> **3 について**: 無理にアナロジーを作らない。ズレた比喩は、無いより有害。

**必ず触れること**（該当する場合）

- **いつ評価されるか** — 起動時か、リクエストごとか、マイグレーション時か
- **どの層の責務か** — Django 本体 / Ninja / Pydantic / ORM / DB
- **失敗したらどうなるか** — どのステータスコードで、どんなボディが返るか
- **発行される SQL** — ORM を扱う回では、実際に出る SQL を必ず見せる

### 4.4 🐍 Python 注（軽量）

初出の Python 文法は **1〜2行の引用**で済ませる。表にしない。深追いしない。

> 🐍 **Python注**: `class Post(models.Model):` の `(models.Model)` は継承。
> TypeScript の `class Post extends Model` と同じ。

**禁止**: 歴史的経緯、PEP 番号、他の書き方との比較、標準ライブラリの周辺紹介。

**例外**（仕組み解剖で厚く扱ってよい）: デコレータ（`@`）、型アノテーション、`with`、クラスの継承。
いずれも Django / Ninja の理解に直結するため。

### 4.7 根拠ルール

**(a) 実行して確かめられる主張**

コードブロックの直後に検証状態を1行で書く。

- `✅ 検証済み: Python 3.12 / Django 5.x / MySQL 8.x`
- `⚠️ 未実行` — **読者が検証するコマンドを必ず併記する**

検証は「起動した」で終わらせない。`curl` の実レスポンス、`python manage.py showmigrations` の出力、`SHOW COLUMNS` の結果、`pytest` の結果まで示す。

**(b) 実行して確かめられない主張**（実務慣習・設計判断）

**一次情報の URL を必須**とする。Django / Django Ninja / Pydantic / MySQL の公式ドキュメント、RFC、OWASP、著名 OSS の実コード。

> 🏢 **実務メモ**: 一覧 API では `select_related` でリレーション先をまとめて取る。
> 1件ずつ取りに行くとクエリが件数ぶん飛ぶ。
> 根拠: https://docs.djangoproject.com/en/stable/ref/models/querysets/#select-related

**URL を出せないなら、その実務メモは書かずに省略する。**

### 4.8 🔓 教材用の簡略化ラベル

学習のために簡略化した箇所は必ず明示する。

> 🔓 **教材用の簡略化**: `SECRET_KEY` を `settings.py` に直接書いている。
> **本番では**: 環境変数から読む。漏れると全セッションとトークンを偽造できる。

### 4.10 おまじない禁止

今の段階で説明しきれない場合のみ:

> ⏭️ **後で回収**: `select_related` の詳細は第2部で扱う。
> 今は「リレーション先をまとめて取る指定」とだけ理解して進む。

宣言した場所で**必ず回収する**。

### 4.11 「分からないまま進んでよい」と明記する ★

**第1部の最初のステップに、次の趣旨を必ず書く。**

> この教材は、1周目で全部分かるようには作られていません。
> あとから出てくるものが、前の意味を決めることが多いからです。
> 分からない箇所には `# TODO: わからん` とコメントを残して、先に進んでください。
> 1周したあと、その印だけを見返せば十分です。

各部の最後でも、同じ趣旨を1行で繰り返す。

### 4.12 コピペ可。ただし1行変える ★

各ステップの実践パートに、次の1行を必ず置く。

> ✋ **コピペで構いません。** ただし打ち終わったら、**どこか1行だけ変えて**動かしてください。
> 変数名でも、文字列でも、数字でもいい。それだけで「読む」が「判断する」に変わります。

   - Docker Compose で MySQL（Docker 学習リポジトリの構成を流用してよい）
3. **完成時のディレクトリ構成**（§10.1）
4. **部ごとのステップ一覧** — 下の表形式。第1部〜第4部すべて
5. **トピック対応表** — 素材の全トピックが、どの部 / 拡張モジュール / 扱わない に入るか。**扱わないものは理由を1行**（SSR 系はここに集まる）
6. **拡張モジュール一覧** — §2.5 の表を `docs/ext/_index.md` にも出す
7. **範囲外の予告** — M3 で詳述する項目

| # | タイトル | 作るもの | 初出（Django/Ninja） | 重要度 |
| --- | --- | --- | --- | --- |
| 1-1 | プロジェクトを作る | `startproject` が通り、開発サーバが起動する | `settings.py`, `urls.py` | 🔴 |

**粒度のルール**: 1ステップの初出は**最大2つ**。3つ以上なら割る。第1部が12ステップを超えるなら、範囲を削る提案をする。

### 5.1 第1部の並び（固定）

この順序は変更しない。**Ninja は後半で初めて出す。**

| # | 内容 | ねらい |

| 1-1 | プロジェクトとアプリを作る | `settings.py` / `urls.py` の役割 |
| 1-2 | **カスタムユーザーモデル**（§2.2） | あとから変えられないので最初に |
| 1-3 | モデルを1つ書く → マイグレーション | 設計図が実物のテーブルになるのを見る |
| 1-4 | 管理画面でデータを入れて見る（§2.4） | 以降の確認手段を確保する |

### 6.1 予測パートの作り方

Django は「書いた宣言が裏で SQL になる」フレームワークなので、予測は**裏で何が起きるか**を狙う。

良い問い: 「この一覧 API を叩くと、SQL は何本飛ぶか。記事が10件あったら?」
良い問い: 「このモデルに項目を1つ足したら、`makemigrations` は何を出力するか」
弱い問い: 「このコードは何をするか」

### 6.2 フェードは「登場回数」で決める

| 登場回数 | 提示量 |
| --- | --- |
| 1回目（初出） | 完成コード全文 + ブロックごとの解説 |
| 2回目 | 骨組みのみ。要点は `# TODO:` の穴埋め |
| 3回目以降 | 要件のみ。解答例は `<details>` |

主要な新概念の登場回数で決める。終盤でも新概念が出れば完成形を出してよい。

## 8. M2 — 部末パック

### 8.1 白紙再現（段階を選べるようにする）★

**いきなり白紙は求めない。** 3段階を提示し、読者に選ばせる。

| 段階 | やること |
| --- | --- |
| **Lv1 穴埋め** | キーワードを伏せたコードを埋める（教材側が用意する） |
| **Lv2 ファイル単位** | ファイルを閉じて、白紙から1ファイル書き直す |
| **Lv3 構成から** | 要件だけ見て、どのファイルに何を書くかから組み立てる |

> ✍️ **白紙再現**: まず Lv1 から。できたら次回 Lv2 に上げる。
> 思い出せなかった箇所に印を付け、**その箇所の 🔬 仕組み解剖だけ**読み返す。

**翌日に実施することを勧める一文を添える。** 直後だと短期記憶で書けてしまい、負荷が足りない。

### 8.2 宿題（Lv1 / Lv2 / Lv3）

- **Lv1 基礎確認** — 本編を少し変えれば解ける
- **Lv2 応用** — 本編の知識を組み合わせて自力実装
- **Lv3 発展** — 本編には無いが実務で必要な拡張

各課題に: 課題 / ヒント（考え方のみ）/ **判定基準（検証可能な形）** / 解答例（`<details>`）。

### 8.3 部の終わりに置くもの ★

各部の最後に、次の3つを必ず書く。

1. **ここまでで何ができるようになったか**（箇条書き3〜5行）
2. **ここで止めても成果物になる**という1行
3. **次の部で何が増えるか**（予告2〜3行）

読者が「続けるか止めるか」を自分で選べる状態にする。

## 10. リポジトリ構成と表記ルール

```

├── docs/
```

**`projects/` は roadmap.sh に提出するもの専用。** ディレクトリ名は URL の末尾（slug）と揃える。各ディレクトリは**自己完結**させる（その中だけで動く）。

### 10.2 表記ルール

- コメントは**日本語**、識別子は**英語**
- コードは動く状態にする。必ず検証状態ラベルを付ける（§4.7）
- 教材とコードを分離しない。解説とセットでドキュメント内に直接掲載する
- 折りたたみは `<details><summary>解答例</summary> ... </details>`
- ファイルパスは毎回明示する（`blog/models.py` に書く、など）
- 差分を示すときは全文か差分かを明示する
- 補った背景知識には `💡補足` を付ける
