### 0.5.1 読み手の特性（実際に起きたことから）

Docker 教材（2026-11）と、その PJ2（Django Ninja + MySQL の Todo API）で起きたこと。

| 起きたこと | 分かったこと |
| --- | --- |
| 7ファイル + 全文置き換えを一度に渡した → コピペだけで終わり、前に足した設定が消えたことにも気づけなかった | **一度に渡す量が多いと、頭が「理解」から「作業」に切り替わる** |
| 「受け入れ基準を自分で書いて」と白紙で頼む → 固まった。ヒントの表だけ渡しても書き出せなかった | **白紙から作るのは苦手。止まる** |

| 「A と B どっち？理由も一言で」と聞く → 毎回きちんと答え、判断もできた | **小さな選択なら、自分の頭で考えられる** |

**読み手の希望（2026-11-14）**: 自分でコードを書きたい。手を動かして考えたい。コードや用語を細かく理解したい。**何をしているか・なぜ必要か・どういう原理で動いているかまで、深く理解したい。** 頭で整理して、地図を自分で描けるようになりたい。
**感想（2026-11-17〜18）**: まだ「なぞっている」感覚がある → 🛠️ 先に自分で決める（§0.5.4）。罫線の図は見にくい・成長感がほしい → 動く図のページ（§0.5.4）。

→ この教材は **「読み手が書く」教材** にする。コピペで進める作りにしない。ただし、白紙で止まらないように **書く量を小さくし、足場（穴うめ・ヒント）を段階的に外す**（§0.5.3）。

### 0.5.2 一度に渡す量の上限

1ステップを **チャンク（ひとかたまり）** に分ける。上限は次のとおり。

| 単位 | 上限 |
| --- | --- |
| 1チャンクで変えるファイル | **1つ** |
| 1チャンクで見せるコード | **差分で15行まで**（新規ファイルは30行まで。超えるならチャンクを割る） |
| 1チャンクで出す新しい言葉 | **1つ**（1ステップの Django / Ninja の初出は §4.2 の2つまで） |
| 1ステップのチャンク数 | **3つまで**。4つ以上必要ならステップを割る |
| 1チャンクの本文（コード・畳んだ部分を除く） | **600字程度** |

**全文置き換えは禁止。** 既存ファイルを変えるときは、必ず「どの行の下に足すか / どの行を消すか」を差分で示す。差分の前後に**変えない行を2行ずつ**添えて、場所が分かるようにする。全文は `<details><summary>変更後の全文（答え合わせ用）</summary>` に畳む。

### 0.5.3 1チャンクの型（先に考える → 自分で書く → すぐ確かめる → 細かく分解）

```markdown
### チャンク1: <図の①に当たる部分>（`accounts/api.py`）

**🤔 先に考える**: <1問だけ。下の3つの形のどれかで答えられる問い>
<details><summary>答え</summary> ... </details>

**🎯 書くもの**: <このコードが何をすればよいかを日本語で1〜3行。どのファイルの、どの行の下に書くか>

**✍️ 自分で書く**: <書く段階（下の表）に応じた足場。読み手がエディタで打つ>
<details><summary>ヒント1: 使う部品の名前</summary> ... </details>
<details><summary>ヒント2: 骨組み</summary> ... </details>
<details><summary>答え合わせ（差分。前後2行つき）</summary> ... </details>

**▶️ 確かめる**: <コマンド1つ> → <何が見えたら OK か>

**🔎 答えの見つけ方**: <分からなくなったら、何を打てば / どこを見れば答えが分かるかを1〜2行。例: 「どの URL が登録されたかは http://localhost:8000/api/docs」「なぜ 401 かは runserver のログの最後の行」。同じ道具を繰り返し出し、読み手の手元に「調べ方の地図」を育てる>

**🔬 1行ずつ分解**: <書いた行を部品に分けた表。下の「分解表の型」>

**📖 しくみ**: <下の3つの見出しで書く。省略しない>
- **何をしているか**: <1〜3行>
- **なぜ必要か**: <これが無いと何が困るか。1〜3行>
- **どういう原理で動くか**: <誰が・いつ・何を読んで・どう動くか。3〜6行。必要なら小さな図>

**🧪 壊してみる**: <1か所だけ消す・変える → どうなるか予想 → 実行 → 元に戻す>
```

**書く段階は、その書き方が何回目に出たかで決める（§6.2 を置き換える）。**

| 何回目か | ✍️ 自分で書く の中身 |
| --- | --- |
| 1回目 | 完成コードを見せる。**コピペ禁止、手で打つ。** 打つ前に 🔬 分解表を読ませる（この回だけ 🔬 を ✍️ の前に置く） |
| 2回目 | **穴うめ**。骨組みを見せ、大事な部分を `___` の空欄にする（空欄は1〜3個）。空欄ごとに「何を見れば埋められるか」のヒントを表で添える |
| 3回目以降 | 🎯 の日本語だけで書く。ヒント1 → ヒント2 → 答え の順に、自分で開けて進める |

- **迷ったら、1つ前の段階に戻す。** 3回目でも書き出せなさそうなら、穴うめにする（読み手から「書けない」と言われる前に）
- **空欄は「前に打ったものから作れる」ようにする。** 例: 「前の回で打ったコマンドから、`docker compose exec api` の部分を外す」
- **1チャンクで読み手が書くのは5行まで。** 大きな白紙は止まる原因なので出さない。5行を超えるならチャンクを割る
- **問いは必ずコードより前に置く。** 予想してから見ると、ただ写すより覚える
- **🤔 の問いの形は3つに限る**: (1) A / B を選んで理由を一言 (2) 図の番号を答える (3) 「〜したらどうなる？」に一言で答える
- 答えに「分からない」と書いてよい、と毎回明記する。ヒントを開けて進むのも「自分で書いた」に数える
- **▶️ 確かめる は毎チャンク必須。** 単独で動きが見えない変更（設定の追加など）は、`uv run python manage.py check`・`uv run python -c "import ..."` などの確認コマンドを置く。最後にまとめて確かめる形にしない
- **🧪 壊してみる は1ステップに1回以上。** 出るエラーメッセージの全文を示し、「どの部品が無いからこのエラーか」を分解表と結びつける

**分解表の型（🔬 1行ずつ分解）**: 書いた行は、**1行も飛ばさず**部品に分ける。

```markdown
`@router.get("/me", auth=JWTAuth())`

| 部品 | 読み方（正式名称） | 意味 | 無いと / 変えるとどうなる |
| --- | --- | --- | --- |
| `@router.get` | アット ルーター ドット ゲット（デコレータ） | 下の関数を「GET で呼ばれる窓口」として Ninja に登録する | 消すと、関数はあるが URL が無い。404 になる |
| `"/me"` | パス | 窓口の住所 | 変えると、呼ぶ住所も変わる |
| `auth=JWTAuth()` | 認証クラス（authentication class） | 関数を呼ぶ前に、身分証（JWT）を確かめる係を付ける | 消すと、だれでも呼べる。401 が出なくなる |
```

**📖 しくみ の書き方**: 正式名称を出したら、**同じ文か次の文で必ず言い換える**。言い換えだけ・正式名称だけ、のどちらにもしない。「原理」は、読み手が頭の中でリクエストや値が動く様子を思い描けるように、**主語（誰が）と順番（いつ）を必ず書く**（例: 「runserver が起動したとき、Django が `urls.py` を読む → リクエストが来るたびに、上から順に住所を比べる」）。

**新しい用語は 📇 用語カード にする。** 1行目には必ず**正式名称**（公式ドキュメントでの呼び名・英語表記）を書く。たとえだけで済ませない。エラーメッセージや公式ドキュメントには正式名称しか出ないため。

```markdown
> 📇 **セッション** — 正式名称: **session**。Django では `django.contrib.sessions`
> かみくだくと: 窓口が「この人は、さっきログインした人だ」と覚えておくための控え。
> 似た言葉との違い: JWT = 本人が身分証を毎回持ってくる。セッション = 窓口が控えを持っていて、本人は控えの番号（Cookie）だけ持ってくる。
> この教材では: `django_session` テーブルの1行
```

### 0.5.4 ステップの始めと終わり

**始め**（`❓ この回の問い` の直後）:

1. **🔁 前回の思い出し** — 前回の内容から1問だけ。答えは畳む。思い出す練習を間隔を空けて入れるため
2. **🧭 全体の中のいま** — アプリ全体（ブラウザ / curl → Django → ミドルウェア → URL → Ninja → ビュー → ORM → MySQL）のどこを今日さわるかを示す。動く図のページ（下の5）の「全体」ボタンで見せる
3. **🗺️ 今日の地図** — このステップの流れを①〜⑤の番号付きで示す。各チャンクの見出しに番号を書く
4. **🛠️ 先に自分で決める** — 前のステップの 🧪 や残った問いで見えた「困りごと」を1つ示し、直し方を読み手に選ばせる（A / B / C と理由一言。白紙にしない）。チャンクはその答え合わせとして並べ、「あなたが選んだ B のとおり〜」のように選択とつなげる。なぞる対象を「教材の手順」から「自分が決めた方針」に変えるため
5. **🖼️ Django の中の図** — ステップの前後の図は Markdown の罫線で描かず、**動く図のページ `docs/visual/django-inside.html`** を使う（Docker 教材で罫線の図が見にくかったため）。ステップのボタンで切り替えるとその時点の図になり、変わった所が光る。部品をクリックすると「正式名称 / かみくだくと / もう少し詳しく / 🔎 確かめるコマンド」が出る。教材の本文には「どのボタンを押して、どこを見るか」を1〜2行書くだけにする
   - ページが無ければ、v2 で最初に書くステップで作る。**ステップを書くたびに、このページも更新する**: ステップを1つ足す（問い・変わったこと・光らせる部品）、図に部品を足す、新しい部品の説明と 🔎 調べ方を足す
   - 同じページに **成長の記録**（ステップごとの ✅ できるようになったこと と 📝 ひとこと）と、覚えた 🔎 調べ方の一覧を置く。成長を目で見える形にするため
   - 本文中の小さな図（3〜5行で済む順番・分かれ道）は、これまでどおり罫線でよい（§4.1(d)）

**終わり**:

1. **✏️ 自分で地図を描く** — 冒頭の 🗺️ 今日の地図を、**読み手が自分で描き直す**。段階は登場回数と同じく外していく: 最初は一部を `＿＿＿` にした穴埋め地図、慣れたら箱の数だけ示した地図、最後は白紙。**地図の各箱に「何を・なぜ」を一言ずつ書き込ませる**。答え合わせは `<details>` に置く
2. **📝 ひとこと** — 「〜だと思っていたけど、実は〜」を1行書く欄を置く。書いたものは `docs/notes.md` に貯める
3. **✅ できるようになったこと** — チェックボックス2〜3個。「〜を説明できる」「〜を予想できる」の形
4. **⏭️ 次の問い** — 答えを全部渡して終えない。次の回の `❓ この回の問い` になる問いを1つ残す（§4.14）

### 0.5.6 詰まったときは「問い」で案内する

読み手は、詰まったときに何を打てばよいかを思いつけない。コマンドも覚えていない。**「自分で調べて」と任せない。** 次の3つの問いを毎回同じ形で示し、どれから聞くかを読み手に選ばせる。出てきたものは一緒に読む。

| 問い | たとえると | この教材でのコマンド |
| --- | --- | --- |
| **Q1. 動いてる？** | 「意識はありますか？」 | runserver のターミナルが止まっていないか / `docker compose ps -a`（DB や追加した箱） |
| **Q2. 何て言ってる？** | 「どこが痛いですか？」 | runserver のターミナルの**最後の1行** / `docker compose logs <サービス> --tail 20` |
| **Q3. 呼んだら返事は来る？** | 「どうなりましたか？」 | `curl -s <URL> -w ' %{http_code}\n'` |

- 返事の番号の読み方を、そのつど表で添える（`000` 返事が来ない / `401` 身分証が無い・古い / `403` 身分証はあるが許可が無い / `404` 住所が無い / `405` やり方がちがう / `422` 書き方がちがう / `500` 中でこわれた → Q2 へ）
- エラーは**最後の1行から読む**。「だれが怒っているか : 何に怒っているか」に分けて見せる
- **書いている途中で保存すると、開発サーバーが途中の状態を読み込んで止まることがある**（エディタの自動保存）。穴うめのチャンクでは、最初にこのことを1行で伝え、「止まったら直して保存し直す。それでも動かなければ runserver を起動し直す」と戻し方を添える
- 教材の各ステップの末尾に「🩺 詰まったら: Q1〜Q3 のどれから聞く？」の1行を置く

## 1. 使い方（部 + モード制）

**1回の応答で1モードだけ。** まとめて出力しない。

### 部（第1部だけで完結する設計）

| 部 | 内容 | ステップ | 終わったとき手元にあるもの |
| --- | --- | --- | --- |
| **第1部** | Django の土台 → JsonResponse 手書き → Ninja → Swagger UI → CRUD | 9〜11 | **動く API が1本**。ここで止めても成果物になる |
| **第2部** | リレーション / 画像 / JWT 認証 / 権限 / 検索 / N+1 / メール / ソフトデリート | 12〜14 | ブログ API として完成 |
| **第3部** | EC 風への拡張（在庫・カート・注文・トランザクション・同時実行） | 8〜10 | 設計の山場 |
| **第4部** | React（3〜4画面） | 4〜5 | 画面から叩ける |
| **PJ** | roadmap.sh のプロジェクト | 1本 | 自力で組んだ別アプリ |
| **拡張** | 任意モジュール（§2.5） | 随時 | 必要になったときだけ |

**第1部が最重要。** 2〜3週間で「動く API が1本ある」状態に到達させる。
第2部以降に進むかどうかは、第1部を終えてから読者が決める。各部の最後に、その判断を促す1行を置く。

### 2.5 拡張モジュール（任意・本編のあとで呼ぶ）

`docs/ext/` に置く。`MX: <name>` で1つずつ生成する。

| name | 内容 | 前提 | 新しく必要なもの |
| --- | --- | --- | --- |
| `celery` | 非同期処理（画像リサイズ・一括メール） | 第3部まで | Redis コンテナ |
| `websocket` | リアルタイム通知 | 第3部まで | Django Channels / Redis |
| `search` | 全文検索 | 第2部まで | Elasticsearch コンテナ |
| `cache` | キャッシュ機構 | 第2部まで | Redis コンテナ |
| `signals` | シグナル（と使いすぎの危うさ） | 第2部まで | なし |
| `drf` | DRF なら同じ API をどう書くか（比較のみ） | 第2部まで | djangorestframework |
| `basic-auth` | Basic 認証（毎回、名前と合言葉を送る）。なぜ使われなくなったか | 第2部まで | なし |
| `session-auth` | セッション認証（Cookie で入場券を持たせる）。CSRF の検査を戻す | `basic-auth` | なし（Django 標準の sessions） |
| `oauth` | OAuth 2.0（合言葉を渡さずに「許可」だけ渡す）。**最後の1ステップで OpenID Connect**（OAuth の上に「この人はだれか」を足す。「Google でログイン」の正体） | `session-auth` | Keycloak コンテナ |
| `web-security` | Web セキュリティ: パスワードのハッシュ（bcrypt など）・HTTPS と SSL/TLS・CORS・CSP・OWASP・サーバーの守り。ステップが多いので `MX: web-security 1` のように分けて呼ぶ | `oauth` | なし |

**認証の3つは、この順に呼ぶ。** 前のやり方で困ったことを、次のやり方が解決する順になっている（なぜなぜでつながる。§4.14）。Token 認証・JWT は第2部（2-6）で済んでいるので入れない。`session-auth` では、第2部の JWT との比較表（§2.3）を思い出させる。外のサービス（Google など）のアカウントは作らせず、**Keycloak を `compose.yaml` に足して、手元だけで試す**（Docker 教材の Compose の知識を使う）。

**認証のあとは `web-security`。** 認証で残った問いが、そのまま Web セキュリティの問いになるため（Basic 認証の合言葉をのぞかれたら？→ HTTPS / Cookie をほかのサイトから悪用されたら？→ CORS・CSRF・CSP / DB の合言葉が盗まれたら？→ ハッシュ）。

**SAML・OpenID（単独）・GraphQL・gRPC・SOAP は入れない**（読み手の決定、2026-11-24）。roadmap.sh/backend で灰色（Order not strict / Learn anytime ＝ いつ学んでもよい）の印が付いているため。必要になったら、この表に行を足す。

**`MX` を呼ばれたら、まず前提を満たしているか確認する。** 満たしていなければ、何が足りないかを伝えて止まる。

`docs/ext/_index.md` に上の表を置き、各モジュールの**ステップ数の見込み**も書く。本編完了時に読者がここを見て選ぶ。

**モジュールを追加したくなったときは、この表に行を足せばよい**（例: 多言語対応は今回入れていないが、あとから足せる。OAuth は v2 で足した）。

roadmap.sh/django のページは JavaScript で描画されるため URL からは読めない。

## 4. 全モード共通の絶対ルール

### 4.1 やさしい言葉で書く ★ この教材の最優先ルール

**(a) 専門用語には必ず言い換えを添える**

正式名称は必ず書く（エラーや公式ドキュメントに出るため）。そのうえで、直後に必ずこれを置く。

> 🧒 **かみくだくと**: マイグレーションは「設計図の変更を、実物のテーブルに反映する作業」。
> 手で SQL を書く代わりに、Django が変更点を見つけて自動でやってくれる。

**(b) 文章の書き方**

- 1文を短く。**1文に読点は2つまで**
- 「〜であり、〜のため、〜という設計」のような積み重ねをしない。文を分ける
- カタカナ語を出したら、直後に日本語で言い換える
- 主語を省かない。「誰が」「何を」するのかを毎回書く

**(c) 共通のたとえ: 役所の窓口**

比喩を毎回変えない。1つを育てて使い回す。

| たとえ | 実際のもの | 初出 |
| --- | --- | --- |
| 窓口に来た人 | リクエスト | 第1部 |
| 受付の案内表 | URL ルーティング | 第1部 |
| 申請書の書式チェック | バリデーション（Ninja のスキーマ） | 第1部 |
| 担当職員 | ビュー関数 | 第1部 |
| 台帳 | データベースのテーブル | 第1部 |
| 台帳を書き換える手続き | マイグレーション | 第1部 |
| 台帳を代わりに引いてくれる職員 | ORM | 第1部 |
| 窓口の順路に置かれた共通の検査 | ミドルウェア | 第2部 |
| 身分証 | JWT トークン | 第2部 |

**(d) 図を入れる**

「積み重なり」「入れ子」「順番」「分かれ道」を説明するときは必ず図を入れる。飾りの図は入れない。

- 形式は**罫線の図**（コードブロックで囲む）を既定とする
- 日本語は半角の2倍幅。**表示幅を計算してから書く**。目視で揃えない
- 図の直後に「どこを見てほしいか」を1〜2行書く
- 分岐する流れは Mermaid の `flowchart` でもよい
- **ステップの前後を比べる図（Django の中がどう変わったか）は、罫線で描かず動く図のページを使う**（§0.5.4）。罫線は本文中の小さな図だけにする

### 4.2 1ステップの分量と新出数 ★

| 項目 | 上限 |
| --- | --- |
| 本文（コード・設定を除く） | **1チャンク600字程度 × 3チャンクまで**（§0.5.2） |
| Django / Ninja の初出 | **2つまで**（1チャンクに1つ） |
| Python 注 | 合計200字以内 |

**超えるならステップを割る。** 前回これが守られず学習が止まった。上限は目安ではなく上限。
やさしく書くために少し長くなるのはよい。ただし、1回に見える量を増やすのではなく、**チャンクやステップを割る**。深い話は `<details>` に畳む。

### 4.3 🔬 仕組み解剖（4点セット）

Django / Ninja の記法・API・挙動が初出のとき、次の4点を必ず埋める。

1. **正式名称** — 公式ドキュメントでの呼び名
2. **実行時に何が起きるか** — Django / Ninja / Pydantic / MySQL のどれが、いつ、何をするか
3. **既知スタック（TypeScript / React）での対応物** — **無い場合は「対応物なし。理由は〜」と書く。これで4点セットを満たしたとみなす**
4. **なぜこの設計なのか** — 他の書き方との比較

> **3 について**: 無理にアナロジーを作らない。ズレた比喩は、無いより有害。

**必ず触れること**（該当する場合）

- **いつ評価されるか** — 起動時か、リクエストごとか、マイグレーション時か
- **どの層の責務か** — Django 本体 / Ninja / Pydantic / ORM / DB
- **失敗したらどうなるか** — どのステータスコードで、どんなボディが返るか
- **発行される SQL** — ORM を扱う回では、実際に出る SQL を必ず見せる

### 4.4 🐍 Python 注（軽量）

初出の Python 文法は **1〜2行の引用**で済ませる。表にしない。深追いしない。

> 🐍 **Python注**: `class Post(models.Model):` の `(models.Model)` は継承。
> TypeScript の `class Post extends Model` と同じ。

**禁止**: 歴史的経緯、PEP 番号、他の書き方との比較、標準ライブラリの周辺紹介。

**例外**（仕組み解剖で厚く扱ってよい）: デコレータ（`@`）、型アノテーション、`with`、クラスの継承。
いずれも Django / Ninja の理解に直結するため。

> 今は「リレーション先をまとめて取る指定」とだけ理解して進む。

宣言した場所で**必ず回収する**。

### 4.11 「分からないまま進んでよい」と明記する ★

**第1部の最初のステップに、次の趣旨を必ず書く。**

> この教材は、1周目で全部分かるようには作られていません。
> あとから出てくるものが、前の意味を決めることが多いからです。
> 分からない箇所には `# TODO: わからん` とコメントを残して、先に進んでください。
> 1周したあと、その印だけを見返せば十分です。

各部の最後でも、同じ趣旨を1行で繰り返す。

### 4.12 読み手が書く（v2 で変更）★

v1 の「コピペ可。ただし1行変える」は**やめた**。コピペで進めると、頭が「理解」から「作業」に切り替わったため（§0.5.1）。

代わりに、§0.5.3 の書く段階（1回目=手で打つ / 2回目=穴うめ / 3回目以降=日本語だけ）で、**読み手がエディタで打つ**。白紙で止まらないよう、書く量は1チャンク5行までにし、迷ったら穴うめに戻す。

### 4.13 禁止事項

1. 解説していない API・設定キー・用語を主線に登場させる
2. 「おまじない」「割愛」で済ませる
3. `⏭️ 後で回収` を宣言して回収しない
4. 検証状態ラベルのないコードブロックを置く
5. 根拠 URL のない実務メモ・アンチパターンを書く
6. 1回の応答で複数モードを実行する
7. **1ステップで Django / Ninja の初出が3つ以上になる**（§4.2）
8. **§0.5.2 の上限（1チャンク1ファイル・差分15行・600字・1ステップ3チャンク）を超える**
9. **専門用語に 🧒 かみくだくと を付けずに出す**（§4.1）
10. 末尾の `?:` 案内（§4.5）を省く
11. SSR（テンプレート / フォーム / クラスベースビュー）を主線で扱う
12. 管理画面のカスタマイズを扱う（§2.4）
13. 第1部で認証・pre-commit を入れる（§2.3 / §2）
14. **既存ファイルを全文置き換えで示す**（§0.5.2）
15. **問いをコードより後ろに置く**（§0.5.3）
16. **白紙で書かせる。** 「自分で調べて」と任せる（§0.5.3・§0.5.6）
17. **実行していないコマンドや出力を、確かめたように書く**（§4.7）

### 4.14 なぜなぜでつなぐ ★ この教材の背骨（v2 で追加）

**知識を並べない。問いを連ねる。** 読み手の要望（2026-09-21、Docker 教材のとき）。

**(a) 各ステップは「問い」で始める** — 冒頭に `**❓ この回の問い**` を置く。その問いは**前の回の答えから生まれたもの**にする。「今回は◯◯を学びます」と書かない。前回の答えを1行で示し、そこから出てくる次の問いを書く。

```markdown
**❓ この回の問い**: 前回、Basic 認証は「毎回、名前と合言葉をそのまま送る」と分かった。
→ **では、1回ログインしたら、2回目からは合言葉を送らずに済ませるには？**
```

**(b) ステップの中も「なぜ」を重ねる** — 仕組み解剖は、事実を並べるのではなく**3〜5回「なぜ」を下る**形で書く。

```
なぜセッション認証では、ログアウトがすぐ効くのか
  → サーバーが控え（セッション）を消すから
      → なぜ控えを消すだけで効くのか
          → 次に来たとき、Cookie の番号に当たる控えが見つからないから
              → JWT はサーバーが控えを持たないので、期限が来るまで使えてしまう
```

**(c) ステップの最後は「次のなぜ」を残して終える** — 答えを全部渡して終えない。**次の問いが立った状態**で終える（§0.5.4 終わりの4）。`⏭️ 後で回収` も、そのための道具。

**(d) まとまりの最後に、なぜなぜの鎖を1枚の図にする** — 部の最後、または関連する MX のまとまり（例: 認証の3つ）の最後に、問いと答えを縦につないだ図を置く。ばらばらに覚えたものが1本道だったと分かるのが目的。

**(e) どこで掘るのをやめるか** — 次のどちらかに当たったら止める。

| 止める条件 | そのときどうするか |
| --- | --- |
| 答えが、その部・その MX の到達点に効かなくなった | 止めて、`docs/99-uncovered.md`（M3）に送る |
| 答えが「そう決まっているから」になった（仕様・歴史的経緯） | 一次情報の URL を出して止める（§4.7(b)） |

掘りすぎは、認知負荷を上げるだけで到達点に近づかない。**止めるのも設計のうち。**
