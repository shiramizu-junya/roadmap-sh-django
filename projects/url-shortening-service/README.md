# PJ: URL Shortening Service

- 出典: https://roadmap.sh/projects/url-shortening-service
- レベル: intermediate
- 作る場所: `projects/url-shortening-service/`
- 本編に無い軸: 一意な短縮コードの生成と衝突処理 / camelCase の JSON / アクセス数の数え方（とリダイレクト）

本編（リポジトリ直下のアプリ）とは**別の独立したアプリ**として作る。

---

## 1. 要件

長い URL を短いコードに変換する REST API。作成・取得・更新・削除・統計の5つの操作を作る。

| # | 操作 | メソッドとパス | 成功 | 失敗 |
| --- | --- | --- | --- | --- |
| 1 | 短縮 URL を作る | `POST /shorten`（本文 `{"url": "..."}`） | 201 | 400（入力が不正） |
| 2 | 元の URL を取得する | `GET /shorten/{shortCode}` | 200 | 404 |
| 3 | 元の URL を更新する | `PUT /shorten/{shortCode}`（本文 `{"url": "..."}`） | 200 | 400 / 404 |
| 4 | 削除する | `DELETE /shorten/{shortCode}` | 204（本文なし） | 404 |
| 5 | 統計を取る | `GET /shorten/{shortCode}/stats` | 200 | 404 |

- 1〜3 のレスポンスは `id`・`url`・`shortCode`・`createdAt`・`updatedAt` の5項目。5 はそれに `accessCount` が加わる
- `createdAt`・`updatedAt` は ISO 8601 の UTC（例: `2021-09-01T12:00:00Z`）。更新すると `updatedAt` だけが変わる
- `shortCode` は**ランダムに作り、重複してはいけない**
- 認証は不要
- 任意: 短縮 URL にアクセスしたら元の URL へ飛ばす（リダイレクト）。API を叩く簡単な画面

🔄 素材からの変更:
- 技術スタックは自由 → **Django + Django Ninja + MySQL**（本編と同じ）
- 出典のパスは `/shorten` から始まる。本編のように `/api/` を前に付けるかは自分で決めてよい（判定基準のコマンドは自分のパスに読み替える）
- 「どのリクエストで `accessCount` を増やすか」は出典に書かれていない → 設計の問い2で自分で決める

## 2. 本編のどれを使うか

| 使う知識 | 本編 | このPJでの使いどころ |
| --- | --- | --- |
| プロジェクト・アプリを作る、`settings.py` / `urls.py` | 1-1 | 本編とは別の設定で起動する |
| モデルとマイグレーション | 1-3 | 短縮 URL の表を1つ作る |
| Ninja のデコレータと `Schema`、`response=` | 1-7・1-8 | 5つのエンドポイントと出力の形 |
| パスパラメータ、`get_object_or_404` | 1-9 | `{shortCode}` で1件を探す。無ければ 404 |
| 更新と `save()` | 1-10 | ただし今回は PATCH ではなく **PUT**（全体を置き換える）。`exclude_unset` は不要 |
| 削除と 204 | 1-11 | そのまま使える |
| pytest と Ninja の `TestClient` | 1-12 | 判定基準をテストで固定する |
| `UniqueConstraint`（一意制約） | 3-2 | 短縮コードの重複を DB でも防ぐ |
| `F()` 式 | 3-4 | アクセス数を、同時アクセスでも取りこぼさず増やす |

**これは不要**:
- カスタムユーザーモデル（1-2）、JWT と権限（2-6・2-7）: 認証が要らない
- `ForeignKey` / `ManyToManyField`（2-2・2-3）、N+1 対策（2-4）: 表が1つだけ
- `transaction.atomic` / `select_for_update`（3-3・3-5）: 1行を `F()` で更新すれば足りる
- ページング・検索（2-11・2-12）: 一覧のエンドポイントが無い
- CORS（4-1）: 画面を作る場合だけ必要

## 3. 本編に無い新しい軸

### 軸1: 一意な短縮コードの生成と衝突処理
- ランダムで、推測されにくく、短いコードを作る（何文字にするか、どの文字を使うか）
- 作ったコードがすでに使われていたらどうするか（作り直す？何回まで？）
- 「先に存在を確認してから保存」だけでは、同時に作られたときにすり抜ける。最後の砦をどこに置くか

### 軸2: JSON の項目名を camelCase にする
- Python は `short_code` のような snake_case、出典の JSON は `shortCode` のような camelCase
- モデルの項目名は snake_case のまま、**出力だけ** camelCase にする方法を探す（Ninja / Pydantic の機能で解決できる）
- 日時の出力形式（UTC、末尾の `Z`）も出典に合わせる

### 軸3: アクセス数の数え方とリダイレクト
- どのリクエストを「アクセス」と数えるか（取得 API？リダイレクト？統計を見ただけでは？）
- 数を増やす処理を、同時アクセスでも正しく動くようにする
- リダイレクトを作る場合: 301 と 302 のどちらを返すか。ブラウザのキャッシュがアクセス数にどう影響するか

## 4. 判定基準

コマンドの出力で自分で判定する。`-i` を付けるとステータスコードも見える。

- [ ] `curl -i -X POST localhost:8000/shorten -H 'Content-Type: application/json' -d '{"url":"https://example.com/very/long"}'` が **201** を返し、本文に `id`・`url`・`shortCode`・`createdAt`・`updatedAt` の5つが camelCase で入っている
- [ ] `url` が無い、または URL の形でない本文を送ると **400** が返る（422 ではない）
- [ ] `GET /shorten/<作ったコード>` が 200、存在しないコードでは **404** の JSON が返る
- [ ] `PUT` で更新すると `url` と `updatedAt` が変わり、`createdAt` と `shortCode` は変わらない
- [ ] `DELETE` が **204** で本文が空。その後の `GET` は 404
- [ ] アクセスを3回してから `GET /shorten/<コード>/stats` を呼ぶと、`accessCount` が3増えている
- [ ] `uv run pytest projects/url-shortening-service` が全部通る。そこに「コードが衝突したら作り直す」テストが含まれている

## 6. 詰まったときの確認順

上から順に、どの層で止まっているかを切り分ける。

1. **HTTP**: `curl -i ...` でステータスコードと本文を見る。404 ならまずパスの書き間違い（`/shorten` と `/shorten/` の違いも含む）を疑う
2. **サーバのログ**: `runserver` を動かしているターミナルに出る例外の最後の行を読む
3. **Django の中**: `uv run python manage.py shell` で、モデルを直接作る・探す。API を通さずに動くかを確かめる
4. **DB**: `docker compose exec db mysql ...` で `SHOW CREATE TABLE` を見る。一意制約やインデックスが本当に付いているか
5. **テスト**: `uv run pytest -x -vv` で、最初に落ちたテストだけを詳しく見る

## 7. ヒント

コードは書かない。考え方だけ。

- **コード生成**: ランダムな文字列は Python 標準の `secrets` モジュールで作れる。`random` は推測されやすいので使わない
- **衝突処理**: DB の一意制約に違反すると、Django は特定の例外を投げる。その例外を捕まえて作り直すと、同時に作られた場合でも重複しない
- **camelCase**: Ninja の `Schema` は Pydantic のモデルなので、項目名の「別名（alias）」を付けられる。全項目に一括で付ける設定もある
- **400 にする**: Ninja には、特定の例外が起きたときのレスポンスを差し替える仕組み（例外ハンドラ）がある
- **PUT の `updatedAt`**: モデルの日時フィールドには、保存するたびに自動で今の時刻を入れるオプションがある
- **アクセス数**: 「読んで +1 して保存」は、同時アクセスで数を取りこぼす（3-4 と同じ問題）。DB の中で足し算させる
- **独立したアプリにする**: このフォルダの中で、本編とは別に `startproject` してよい。本編の DB を汚したくないなら、MySQL に別のデータベースを作る
