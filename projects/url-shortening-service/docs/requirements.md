# 要件: URL Shortening Service

AI に実装させるための要件。**ここに書いていないことは、AI が勝手に決めてしまう**と思って書く。

今回の範囲: `POST /shorten`（短縮 URL を作る）だけ。ほかのエンドポイントは、この1本を一周してから足す。

例外: Ninja が自動で作る `/docs`（Swagger UI）と `/openapi.json` は**残す**。API を試したり、入出力の形を確かめたりするために使う。

---

## POST /shorten

### 何をするか
<!-- 1〜2行で。誰が、何を送ると、何が起きるか -->

利用者が長い URL を送ると、その URL に対応する6文字の短縮コードを発行して返す。すでに登録済みの URL なら、新しく作らずに既存のコードを返す。

### リクエスト
<!-- パス（/api/ を付ける？）、ヘッダー、本文の JSON 例 -->

- パス: `POST /shorten`（`/api/` は付けない。roadmap.sh の課題に合わせる）
- 本文: `url` だけを受け付ける。**それ以外の項目は無視する**（エラーにしない）
- 短縮コードを利用者が指定する機能は**作らない**。`shortCode` が送られてきても、ほかの項目と同じく無視する
- 送られた `url` は**書き換えずにそのまま保存し、そのまま返す**（末尾に `/` を足す、大文字を小文字にする、などの正規化はしない）
- 「登録済みの URL」かどうかは、**送られた文字列が完全に一致するか**で判定する。`https://example.com` と `https://example.com/` は別の URL として扱う
- 「URL の形をしている」かどうかは、Django の `URLValidator(schemes=["http", "https"])` で判定する（`http://localhost:8000` は通る、`http://intranet` のようにドメインの後ろが無いものは 400）

```json
{"url": "https://example.com/very/long/path"}
```

### 成功したとき
<!-- ステータスコード、本文の JSON 例（項目名・型・日時の形式まで） -->

- `id`: **数値**（Django の主キーのまま）。roadmap.sh の例は文字列 `"1"` だが、合わせない
- `createdAt` / `updatedAt`: **UTC で、末尾に `Z`、秒まで（小数なし）**。例: `2021-09-01T12:00:00Z`。日本時間（`+09:00`）や `+00:00` の形にはしない
- 項目名は camelCase（`shortCode`・`createdAt`・`updatedAt`）

```json
{
  "id": 1,
  "url": "https://example.com/very/long/path",
  "shortCode": "abc123",
  "createdAt": "2021-09-01T12:00:00Z",
  "updatedAt": "2021-09-01T12:00:00Z"
}
```

### 失敗したとき
<!-- どんな入力が「不正」か。そのときのステータスコードと本文の JSON 例 -->
<!-- 考えるポイント: url が無い / 空文字 / URL の形でない / 長すぎる / javascript: など危ないもの -->

次の入力はすべて **400** で弾く。Ninja の既定（422）のままにしない。

エラーの本文は、どの場合も `{"detail": "<日本語のメッセージ>"}` の形にする（Ninja の `HttpError` と同じ形）。
メッセージの文言は自由。ただし**何がダメだったのかが利用者に分かる日本語**にする（「不正な入力です」だけは不可）。
テストでは、ステータスが 400 であることと、`detail` が空でない文字列であることだけを確かめる。

```json
{"detail": "url は http または https で始まる必要があります"}
```

| # | 入力 | ステータス | 本文 |
|---|---|---|---|
| 1 | 本文が空、または `url` が無い | 400 | `{"detail": "..."}` |
| 2 | `url` が空文字 `""` | 400 | `{"detail": "..."}` |
| 3 | `url` が URL の形をしていない（`abc` など） | 400 | `{"detail": "..."}` |
| 4 | `http` / `https` 以外（`ftp://`、`javascript:alert(1)` など） | 400 | `{"detail": "..."}` |
| 5 | 2048文字を超える URL（2048文字ちょうどは OK。文字数は Python の `len()` で数える） | 400 | `{"detail": "..."}` |
| 6 | `url` が文字列でない（`{"url": null}`、`{"url": 123}` など） | 400 | `{"detail": "..."}` |
| 7 | JSON として壊れている | 400 | `{"detail": "..."}` |
| 8 | 本文が JSON のオブジェクトでない（`[]` など） | 400 | `{"detail": "..."}` |

日本語を含むドメインやパス（`https://例え.jp/パス`）は受け付ける。

対象外（今回は弾かない）: 自分自身の短縮 URL を登録すること。リダイレクトを作るときに改めて考える

### 短縮コードのルール
<!-- 長さ、使う文字、重複したときどうするか（何回まで作り直す？それでもダメなら？） -->

- 長さ: **6文字ちょうど**
- 使う文字: **英大文字・英小文字・数字の62種類**（`A-Z`・`a-z`・`0-9`）。記号は使わない
- 作り方: **ランダム**。連番やタイムスタンプなど、推測できる作り方はしない
- 重複したら: すでに使われているコードだった場合は作り直す。**保存を試すのは、最初の1回を含めて合計5回まで**
- 5回とも重複したら: **500** を返す（本文は 400 のときと同じ `{"detail": "..."}` の形）
- 同時に2つのリクエストが来ても、同じコードが2つできてはいけない（別々の URL に同じコードが付くのは致命的なので、必ず防ぐ）
- 一方、**同じ URL が同時に2回送られた場合**に、その URL のコードが2つできてしまうことは**許す**（今回は対象外）。どちらのコードでも正しい URL に対応するので実害がないため。同時でなければ、受け入れ条件どおり既存のコードを返す

### 受け入れ条件
<!-- 「〜を送ると〜が返る」の形で、確かめられる文にする。これがそのままテストと curl の判定基準になる -->

**成功するとき**
- [ ] `{"url": "https://example.com/very/long/path"}` を送ると **201** が返り、本文に `id`・`url`・`shortCode`・`createdAt`・`updatedAt` の5つがある
- [ ] そのときの `id` は数値、`shortCode` は英数字ちょうど6文字である
- [ ] `createdAt` と `updatedAt` は `2021-09-01T12:00:00Z` の形（UTC、`Z` 付き、小数なし）で、作った直後は同じ値である
- [ ] `{"url": "...", "foo": 1, "shortCode": "mine"}` を送っても 201 が返り、`shortCode` は `mine` ではなくランダムなコードになる
- [ ] すでに登録済みの URL をもう一度送ると、新しく作らずに**前と同じ `shortCode`** が返り、ステータスは **200**（新規作成の 201 と区別する）。本文の形は 201 のときと同じ。データは何も変わらないので、`updatedAt` も前のままである

**失敗するとき**
- [ ] `{}`、`{"url": ""}`、`{"url": "abc"}`、`{"url": "javascript:alert(1)"}` を送ると、どれも **400** で、`detail` が空でない文字列で返る
- [ ] 2048文字ちょうどの URL は 201、2049文字の URL は 400 が返る

**重複するとき**
- [ ] コードが5回連続で重複する状況を作ると **500** が返り、本文は `{"detail": "..."}` の形である
- [ ] 同じ `short_code` で2件保存しようとすると、2件目は DB の一意制約によってエラーになる（DB に一意制約が本当に付いていることの確認）
- [ ] 1回目の保存で重複エラーが起きたら、別のコードで作り直して 201 が返る

本当に同時にリクエストを送るテスト（スレッドなど）は作らない。同時アクセスでの重複は DB の一意制約が防ぎ、上の2つのテストで「DB が弾く」「弾かれたら作り直す」の両方を確かめるため。
